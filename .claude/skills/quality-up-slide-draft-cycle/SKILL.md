# slide-draft.md の 1 サイクル品質向上

このスキルは `slide-draft.md` のクオリティを 1 サイクル分上げる。

## 入力

- `slide-draft.md` (プロジェクトルートにある原稿)
- 参考: `outline.md`、`slide-outline.md` (聴衆設定 / ブロック役割の文脈)

## 動き方

### 0. サイクル開始時の確認

- `slide-draft.md` の現状を Read で確認する (前サイクルからの変更点を把握、Claude の認識と実ファイルがズレないように)
- `slide-draft-history.md` が存在すればサイクル番号を確認 (今回が何サイクル目か)

### 1. 4 視点の並行評価 (事実確認を含む)

次の 4 サブエージェントを **同時に** spawn する:

1. **`validity-checker`**: 事実 / 論理視点 — 文書内の事実誤認の疑い、論理破綻、整合性
2. **`writing-style-checker`**: 表現 / 口調視点 — ですます調、冗長・抽象表現、磨き
3. **`audience-checker`**: 聴衆視点 — 混在聴衆への伝わりやすさ、ブロック間のつながり、図案メモの妥当性
4. **`fact-checker`**: 事実確認 — 公式情報源で事実を確認。`[要確認: ...]` マーカーや、不確かな情報 (リリース年、インストール手順、料金体系、機能仕様など) を WebFetch / WebSearch で裏取りし、出典 URL 付きで報告

各サブエージェントへの依頼に必ず含める:
- `slide-draft.md` を読んで、自分の視点で改善点を箇所 / 問題 / 改善案の形で報告する
- LT のコンテキスト (聴衆、目的、各章の役割) は `outline.md` / `slide-outline.md` から把握させる
- **`slide-draft-history.md` を読んで、前サイクルで確認済 / 適用済の指摘は再掲しないよう指示**する (重複指摘を防ぐ)
- `fact-checker` には、前サイクルで確認済の事実 (年号 / インストール手順など) は再調査不要と明示する
- **サイクル 2 以降は「重要度の高い 5 件以内に絞る」と指示**する (サイクル進行に応じて指摘を厳選、ノイズを減らす)

並行起動が重要 (4 視点を独立に評価することで、互いに引きずられないようにする)。

### 2. 改善の適用 (Claude の判断ハードルを下げる)

4 視点の指摘を集約し、`slide-draft.md` を直接編集する:

- 複数視点で指摘された箇所 → 必ず適用
- 1 視点だけの指摘 → 内容に合理性があれば適用
- 視点同士で矛盾する指摘 → スキル本体の判断で良い方を選ぶ。判断理由を履歴に残す
- `fact-checker` が確認できた `[要確認: ...]` → 出典付きで埋める。公式情報が見つからなければ「未確認」として残す
- 図案メモ `[図案: ...]` → `audience-checker` の指摘に従い、必要に応じて修正・追加・削除する

**Claude の判断ハードルを下げる** (細部の 1 件ずつをユーザーに確認しに行く運用はスキルの価値を下げる):
- 自動適用するもの: 表現磨き / 既存方針に従う構造調整 / 整合性確保 / 事実誤認の修正 / 図案メモの整理など、明確な改善方向があるもの
- ユーザー判断を仰ぐもの: 設計方針が分かれる重要な選択 / ユーザー固有の情報が必要なもの / 影響範囲が大きく後戻りしにくいもの / ユーザーが意図的に入れた内容の上書きになるもの
- 判断目安: 「これは独断で進めても、後で『なぜそうした?』と聞かれて答えられるか」 — 答えられるなら自動適用

### 3. 履歴の記録

`slide-draft-history.md` をプロジェクトルートに作成 (なければ新規)、サイクル分を追記する:

```
## サイクル {N} ({日時 YYYY-MM-DD HH:MM})

### 4 視点の主な指摘
- [validity-checker] (要点)
- [writing-style-checker] (要点)
- [audience-checker] (要点)
- [fact-checker] (要点 — 確認できた事実 / 未確認のもの)

### 適用した変更
- {章}.{ブロック}: (変更内容)

### 視点同士の矛盾とその判断 (該当があれば)
- (どの指摘とどの指摘が矛盾し、なぜ片方を選んだか)

### fact-checker で確認できた [要確認] (埋めた)
- (元の要確認文 → 埋めた内容、出典 URL)

### fact-checker で未確認 (残)
- (要確認文と、なぜ未確認のままか)

### ユーザー判断必要な [要確認] (残)
- (要確認文と何を判断してほしいか)
```

### 4. ユーザーへの報告

サイクル終了後、ユーザーに以下を報告:
- 適用した主な変更 (要約、3-5 項目程度)
- fact-checker で埋めた `[要確認]` の概要
- fact-checker で未確認のまま残った事実 (出典が見つからなかったもの)
- **ユーザー判断必要な `[要確認]` の一覧** (これがあれば、ユーザーが解消するのを待つ)
- 履歴ファイル `slide-draft-history.md` を更新したこと

## 重要な原則

- 1 サイクルで `slide-draft.md` 全章を見直す (浅く広く、特定の章に偏らない)
- 既に質が高い箇所には触らない (= 「改善できる箇所だけ」)
- 改善は具体的かつ検証可能に
- 履歴は事実を漏れなく残す (整形より漏れ防止を優先)
- 自動解消できない `[要確認]` を勝手に推測で埋めない (ユーザー判断に残す)
- **ユーザーが過去のサイクルで意図的に入れた内容 / 表現は、勝手に削らない** (上書きする前にユーザー判断を仰ぐ)
- **機械的な一括置換は避ける** (用語変更などでも、1 箇所ずつ文脈を見て判断する)
